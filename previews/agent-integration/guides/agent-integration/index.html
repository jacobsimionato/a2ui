How to Integrate A2UI into an Agent

Integrate A2UI UI generation into an agent using the Agent SDKs to stream validated interactive surfaces to clients and respond to user actions across turns.

If you are building the client application instead, see How to Integrate A2UI into a Client. To register custom widgets beyond the built-in Basic catalog, see How to Define a Catalog, and for wire vs. compact DSL trade-offs see Swappable Inference Formats. Agent SDKs are available for TypeScript, Python, and Dart, while Swift and Kotlin target client-side rendering (see SDKs).

Step 1: Install dependencies

Install the Agent SDK and Core SDK packages for your language:

  • TypeScript
  • Python
  • Dart

Step 2: Initialize the A2UI generator

Create a shared generator configured with your component catalogs, your chosen inference format, and a session map to track active surface state across turns.

The steps below build a sample e-commerce order assistant service, though an agent can serve any domain. Register the built-in v1.0 Basic catalog (and any custom domain catalogs) when your agent starts, and inject a model-streaming callback so the service stays decoupled from any specific LLM SDK or transport. The generator also sets the inference format—Express is the default, instructing the model to emit compact <a2ui> blocks that compile into validated A2UI JSON messages, and can be swapped for other formats such as Direct JSON (see Swappable Inference Formats for details):

  • TypeScript
  • Python
  • Dart

Step 3: Build the system prompt and stream A2UI messages

On each conversation turn, generate the A2UI system prompt instructions for the session and stream the language model’s token output through a request processor to emit validated A2UI messages.

Look up or initialize the session’s renderer state, create a request processor bound to that state, and append its generated prompt snippet to your agent’s role instructions. If each chat turn creates an independent surface instead of updating earlier ones, omit the session state so every response validates from an empty state.

As tokens arrive from the language model, feed each chunk into the processor’s stream and close the stream when generation finishes. The stream reader closes partial string properties such as text incrementally as tokens arrive, updates the session state, and yields createSurface, updateComponents, updateDataModel, and deleteSurface messages as soon as they are ready:

  • TypeScript
  • Python
  • Dart

Step 4: Handle user actions

Process incoming user action messages from the client renderer and stream back UI updates for the active surface.

When a user interacts with a component such as Confirm order, the client renderer resolves the action’s context bindings against its local data model and sends an action message to the agent. Your action handler can execute backend business logic (for example, confirming the order in your database) and either trigger a follow-up turn with the action details so the model updates "order_summary" in place, or emit deterministic updateDataModel and updateComponents messages directly:

  • TypeScript
  • Python
  • Dart

Step 5: Connect to a transport

Connect your agent service to the transport channel your application uses to exchange messages with clients.

A2UI is transport-agnostic: an agent can exchange JSON envelopes over Server-Sent Events (SSE), WebSockets, HTTP chunked responses, gRPC, in-process streams, or standardized agent protocols such as AG-UI, A2A, and MCP (covered in Connect to agent frameworks and transports). Whichever transport you choose, route incoming user prompts to your turn runner, route incoming client action messages to your action handler, and forward each emitted A2UI message over your outbound channel.

The example below exposes the order assistant behind a minimal HTTP endpoint (POST /api/agent) that streams A2UI messages over Server-Sent Events (text/event-stream). On follow-up turns, the model passes update=true in surface("order_summary", update=true) to update the surface already tracked in the session state:

Additional steps

Negotiate client capabilities

Negotiate active catalogs per request when your agent serves external clients or multiple shipped app versions with different widget sets.

If your team owns both the agent and the client app, targeting your known catalogs directly as in Step 3 avoids runtime capability plumbing. Otherwise, register every catalog your agent supports on the generator, read metadata.a2uiRendererCapabilities (or metadata.a2uiClientCapabilities for v0.9.1 clients) on each request, and verify that the negotiated processor accepts the existing session state in case the caller’s catalogs changed. In TypeScript and Python, all catalogs on a single generator must target the same protocol version, so maintain a separate v0.9 generator when serving both v1.0 and v0.9.1 clients (Dart groups mixed-version catalogs automatically):

  • TypeScript
  • Python
  • Dart
Wire format: inbound renderer capabilities metadata

Client renderers attach their supported capabilities in transport metadata (a2uiRendererCapabilities under "1.0" in v1.0, or a2uiClientCapabilities under "v0.9" in v0.9.1):

v1.0 renderer_capabilities.json ↗ v0.9.1 client_capabilities.json ↗

Synchronize client data models and handle function RPCs

Read synchronized client data-model snapshots, execute agent-side function RPCs, and recover from client validation errors alongside standard user actions.

  1. When a surface is created with sendDataModel: true (surface("order_summary", sendDataModel=true) in Express), the renderer attaches that surface’s full data model, including local two-way input edits, under metadata.a2uiRendererDataModel.surfaces[surfaceId] (metadata.a2uiClientDataModel.surfaces[surfaceId] in v0.9.1) on every message it sends to the agent.
  2. callAgentFunction (v1.0 only) invokes a catalog function hosted on the agent and expects a correlated agentFunctionResponse without running an LLM turn. Attach function handlers to your catalog and dispatch incoming envelopes through the SDK’s renderer-to-agent message processor, which validates arguments against the function schema and answers unknown functions or handler failures with a structured error reply.
  3. error reports a client-side VALIDATION_FAILED or function failure (code, surfaceId, message) that you can pass into a follow-up turn so the model repairs the surface.
  • TypeScript
  • Python
  • Dart

Validate whole responses and customize inference formats

Validate complete model responses atomically and customize catalog scope or inference syntax to fit your model and deployment architecture.

When you prefer whole-response validation over incremental token streaming, parse the completed model text in a single call on the request processor. If the model invents an unknown component, omits root, or leaves a dangling child ID, the session state rolls back every change from that turn and raises a validation error whose message you can feed back to the model for a self-correcting retry.

You can also customize catalog scope and output formatting on the generator:

  1. Prune large catalogs to the exact components and functions a workflow needs using component and function pruning transformers.
  2. Configure Express format options (such as allowed message types, default surface ID, or progressive string keys), or switch to the Direct JSON format if your model or fine-tuned checkpoint writes raw JSON envelopes inside <a2ui-json> tags (see Swappable Inference Formats).
  3. In single-process TypeScript or Dart apps where the agent and renderer share memory, wrap the request processor in StreamedAnswer to update a local MessageProcessor directly without JSON serialization.
  4. In Python, compose reusable server-side component templates with @macro and expand them into Basic catalog primitives via MacroExpander (from a2ui.transformers import MacroExpander, macro) so mobile and web clients render new composite layouts without a client release.
  • TypeScript
  • Python
  • Dart

Connect to agent frameworks and transports

Plug the A2UI generator and request processor into standard agent frameworks and protocols instead of writing custom transport plumbing:

Google ADK

Use the ADK integration package to manage per-session request processors, inject A2UI prompt instructions without colliding with ADK {variable} state templating, expose the client A2UI toolset, and bridge A2A events and function RPCs:

Avoid raw prompt strings in LlmAgent.instruction

ADK substitutes {name} placeholders in plain string instructions from session state. Concatenating processor.prompt_snippet into a raw LlmAgent.instruction string raises KeyError on A2UI braces (such as ${expression} or \p{XID_Start}). Always wrap your instruction in A2uiInstruction, which resolves your own {store_city} template variables while leaving the A2UI prompt untouched.

A2A protocol

Use the A2A integration package to advertise A2UI support on your agent card, negotiate the A2A Extension Specification per request, stream A2UI messages as application/a2ui+json data parts, and answer inbound function RPCs:

AG-UI and CopilotKit

Enable A2UI on CopilotRuntime to stream A2UI surfaces over AG-UI across Python and TypeScript agent backends.

When injectA2UITool: true is set (or when the frontend supplies a catalog), CopilotKit injects the A2UI generation tool and translates tool calls and state deltas into AG-UI events across integrations including Google ADK (ag_ui_adk), LangGraph (CopilotKitMiddleware), and AWS Strands (@ag-ui/aws-strands).
