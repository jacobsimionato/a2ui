Overview: How A2UI Works

A2UI lets an AI agent describe an interactive UI as a stream of JSON messages that a client app renders with its own native widgets. Below you’ll find the pieces on each side of the connection, how they fit together, and one request traced from the user’s prompt to a button tap.

The central idea is that layout and data travel separately. The agent sends the component tree when the structure changes, and sends data values on their own, addressed by JSON Pointer. Controls on the client can then update local state without a round trip to the agent, backend services can write values into the UI without regenerating it, and the model spends fewer tokens because it doesn’t repeat the layout every time a value changes.

How the pieces fit together

The diagram below has two sides. On the server, your agent holds two inputs: a component catalog (catalog.json) and your domain tools, such as a flight search API. The A2UI Agent SDK wraps two parts: a skill generator that turns the catalog into prompt instructions, and a compiler that parses and validates what the model writes. Your agent code and LLM runtime sit outside the SDK. They take the generated instructions, call the model, and pass its output to the compiler. The compiler emits updateComponents (layout) and updateDataModel (data) messages over a transport such as AG-UI, A2A, MCP, or WebSockets. On the client, your app hosts the A2UI Renderer, which draws the agent’s UI with native widgets inside a region of your app’s screen called a surface. When the user taps a button, the renderer sends an action message back to the agent. Purple marks code you write on the server, blue marks your client app, and the teal dashed outlines mark the A2UI libraries on each side.

The main parts

Component catalog

A component catalog is a JSON Schema document that both sides agree on. It declares:

  • Components: the widgets the agent may use, such as Card, Column, Row, Text, TextField, and Button in the basic catalog.
  • Properties: the props each component accepts (for example variant on Button), validated with standard JSON Schema keywords.
  • Children: where child components go, either a single child ID or a children list.
  • Functions: client-side functions such as formatCurrency and validation checks such as required.

You can use the A2UI basic catalog or write your own catalog with components specific to your app. A travel app might add a FlightCard, for example.

Learn more in Catalogs, Components, and Functions.

A2UI Agent SDK

The A2UI Agent SDK is a server-side library for TypeScript, Python, and Dart. It contains two parts:

  • Skill generator: reads the catalog and produces the system prompt instructions, examples, and grammar rules the model needs to write UI.
  • Compiler and validator: parses the model’s output as it streams, whether it’s written in a compact inference format like Express or as direct JSON. It checks each component against the catalog schema and emits A2UI wire messages.

Because the SDK handles parsing and validation, your agent code never assembles wire messages by hand.

Learn more in Agent SDKs and Inference Formats.

Your agent and LLM runtime

Your agent code sits outside the Agent SDK. It’s the orchestration logic you already write:

  • Framework and model: any LLM runtime works, including the Google GenAI SDK, Agent Development Kit (ADK), A2A agents, Anthropic, OpenAI, or LangChain.
  • Domain tools: flight search, authentication, reservations, or whatever your app needs. The agent uses these alongside the generated A2UI skill.
  • Request loop: when a user sends a message, the agent calls its tools, reasons over the results, and passes the model’s UI output to the A2UI compiler.

Layout and data messages

A2UI keeps the component tree and the data it displays in separate messages:

  • Layout (updateComponents): a flat array of components. Each one has a unique id, a component type, its properties, and the IDs of its children.
  • Data (updateDataModel): a JSON value written at a JSON Pointer path in the surface’s data model, such as /outbound/price.

Keeping them apart has three practical effects:

  • Data updates don’t resend layout: the agent or a backend can push new prices or status values without regenerating the component tree.
  • Local interactions stay local: sliders, text fields, and steppers write to the client’s data model directly, so the UI responds immediately without waiting for the agent.
  • Backends can supply exact values: services can write values such as fares or booking IDs straight into the data model, so they come from your records rather than from model output.

Learn more in Messages and Data Binding.

Your app and the A2UI Renderer

Your client app embeds an A2UI Renderer for Flutter, Web (Lit, React, Angular), SwiftUI, or Jetpack Compose. The renderer handles:

  • Surfaces: a createSurface message gives the renderer a surfaceId and a catalog. The surface is the region of your app where the agent’s UI appears; the rest of the screen is yours.
  • Native widgets: the renderer maps each catalog component to a platform widget, such as Button to a Flutter ElevatedButton, a web <button>, or a SwiftUI Button.
  • Data binding: properties bound to the data model (@path in v1.0, path in v0.9.1) update whenever the bound value changes.
  • Actions: when the user taps a control with an action, the renderer resolves the action’s context against the data model and sends an action message to the agent.

Learn more in Renderer SDKs and Actions and Functions.

Following one request

The rest of this page follows a flight booking from catalog to button tap. The work happens in this order: you define the catalog, the SDK generates a skill from it, the agent prompts the model, the SDK compiles the model’s output, and the client renders the result.

Define the catalog

You define the components the agent may use in catalog.json. A travel app might pair the basic catalog with its own components such as FlightCard. Each component describes its properties with JSON Schema, and the Agent SDK validates model output against those schemas, so the agent can only send components the client knows how to draw.

Generate the skill

Before calling the model, the Agent SDK reads the catalog and generates the instructions the model needs:

  • A compact description of each component, its properties, and their constraints.
  • Grammar rules for the chosen inference format, such as Express.
  • Text you place in the agent’s system prompt or tool configuration.

Prompt the model

The user types a request in the client app:

“Berlin to San Francisco today, and two tickets back on Oct 19.”

Your agent then:

  1. Calls a domain tool, for example searchFlights(from: "BER", to: "SFO", date: "2026-10-12"), to get flights and prices.
  2. Decides that a form with passenger counts is more useful here than a paragraph of text.
  3. Prompts the model with the flight data and the generated A2UI skill.

Compile and validate the output

The model streams its answer. Instead of writing wire JSON directly, it can use a compact inference format such as Express:

The Agent SDK compiler processes the stream as it arrives:

  1. Parsing: turns incoming tokens into an intermediate representation.
  2. Validation: checks that each component exists in the catalog and that its properties match the schema. Invalid output is reported as soon as it appears.
  3. Emitting messages: produces the wire messages:
    • createSurface opens the surface on the client.
    • updateComponents sends the validated component list.
    • updateDataModel sends the initial data values.

Render on the client

The client receives the messages over its transport (for example AG-UI, A2A, MCP, or a WebSocket), and the A2UI Renderer:

  1. Creates the surface identified by surfaceId.
  2. Builds the widgets, starting at the component with ID root and following each child and children reference.
  3. Binds data: each bound property (such as {"@path": "/outbound/pax"} in v1.0 or {"path": "/outbound/pax"} in v0.9.1) subscribes to that path in the surface’s data model.
  4. Handles local changes: when the user taps + on the outbound passenger count, the FlightCard writes the new value to /outbound/pax. Every widget bound to that path updates, and nothing is sent to the agent.
  5. Sends the action: when the user taps Confirm booking, the renderer resolves the context paths against the current data model and sends an action message to the agent.

Capability negotiation

Before the agent generates any UI, the client tells it which catalogs it can render. The agent then only uses components the client supports.

Advertising capabilities

The renderer sends its capabilities in transport metadata:

  • In v1.0 (Candidate), the metadata key is a2uiRendererCapabilities, keyed by "1.0".
  • In v0.9.1 (Active), the metadata key is a2uiClientCapabilities, keyed by "v0.9".

Where the metadata goes depends on the transport:

  • A2A: capabilities ride on the metadata of each message and apply to that turn. Leaving them off a later message withdraws A2UI support for that turn.
  • MCP: capabilities are sent once during session initialization and apply to the whole session.

Capability fields

FieldTypeDescription
supportedCatalogIdsstring[]Required. IDs of the catalogs the renderer has registered. Components from several supported catalogs can be mixed on one surface.
inlineCatalogsobject[]Optional. Full catalog definitions sent in the metadata. Send these only if the agent advertises acceptsInlineCatalogs: true in its capabilities.

Choosing a catalog

When the agent receives the capability object, it picks the catalog for the surface:

  • Your own catalog: if the client lists the domain catalog the agent wants (for example https://example.com/catalogs/travel/v2.json), the agent uses it and its domain components.
  • Basic catalog: if not, the agent can build the UI from basic catalog components such as Card, Text, Button, and Column (https://a2ui.org/specification/v1_0/catalogs/basic/catalog.json in v1.0, https://a2ui.org/specification/v0_9/catalogs/basic/catalog.json in v0.9.1).
  • No A2UI: if the client sends no capabilities, the agent replies with plain text or Markdown instead.

The agent then runs the skill generator for the chosen catalog, and the createSurface message it sends names that catalog in catalogId.
