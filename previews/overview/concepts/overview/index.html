Overview: How A2UI Works

A2UI lets an AI agent describe an interactive UI as a stream of JSON messages that a client app renders with its own native widgets. Below you’ll find the mechanics on each side of the connection, how they fit together, and one request traced from the user’s prompt to a button tap.

Generating UI

On the server, you configure the A2UI Agent SDK with a component catalog (catalog.json) that describes the UI components and functions available to render on your client. From that catalog, the SDK’s skill generator produces an A2UI skill containing prompt instructions and grammar rules. Your agent code and LLM runtime sit outside the SDK: they take the generated A2UI skill alongside your domain tools (such as a flight search API), call the model, and pass its UI output to the SDK’s compiler. The compiler parses and validates the content against the catalog, then sends layout (updateComponents) and data (updateDataModel) messages over a transport such as AG-UI, A2A, MCP, or WebSockets.

On the client, your app hosts an A2UI Renderer, which draws the UI with native platform widgets inside a region of your screen called a surface. Controls bound to the surface’s data model update state locally as the user interacts with them, and user triggers such as button taps send action messages back to the agent.

While this page focuses on generating UI at request time, A2UI content can also be authored in advance and sent as a static payload (for example, returned from an MCP server via an agent to a client), following a traditional server-driven UI pattern.

Step-by-step Generation

The rest of this page traces a flight-booking request through each stage of the pipeline: defining the catalog, generating the skill, prompting the model, compiling and validating the output, rendering the surface on the client, and handling user actions.

Define the catalog

You define the components and functions your client can render in catalog.json. A travel app might pair the basic catalog with domain components such as FlightCard. Prompt the model

The user types a request in the client app:

“Berlin to San Francisco today, and two tickets back on Oct 19.”

Your agent then:

  1. Calls its domain tools, for example searchFlights(from: "BER", to: "SFO", date: "2026-10-12"), to get flights and prices.
  2. Decides that a form with passenger counts is more useful here than a paragraph of text.
  3. Loads the generated A2UI skill and prompts the model with the flight data.

Compile and validate the output

The model streams its answer. Instead of writing wire JSON directly, it can use a compact inference format such as Express:

The Agent SDK compiler processes the stream as it arrives:

  1. Parses incoming tokens into an intermediate representation.
  2. Validates that each component exists in the catalog and that its properties match the schema, reporting invalid output as soon as it appears.
  3. Emits the wire messages: createSurface opens the surface on the client, updateComponents sends the validated component list, and updateDataModel sends the initial data values.

Render on the client

The client receives createSurface, updateComponents, and updateDataModel over its transport (for example AG-UI, A2A, MCP, or a WebSocket), and the A2UI Renderer:

  1. Creates the surface identified by surfaceId and stores the initial values in its data model.
  2. Resolves the flat component list and data model into a hierarchical node layer starting at root, following each child and children ID and binding path references (such as /outbound/pax) to their values in the data model.
  3. Builds the native widgets from that node tree and subscribes each widget to updates on its bound properties.

At this point, the client’s node layer joins the component hierarchy with the resolved values from the data model. Card (root) wraps Column (layout_col), which contains the two FlightCard nodes with their bound prices and passenger counts alongside Button (submit_btn) and its Text label:

Handle user actions

Once the surface is rendered, the renderer handles local state edits on the client and sends explicit user triggers back to the agent:

  1. When the user taps + on the outbound FlightCard to raise the passenger count to 2, FlightCard writes 2 directly to /outbound/pax in the surface’s data model. Every node bound to /outbound/pax updates in place, and nothing is sent to the agent.
  2. When the user taps Confirm booking, the renderer triggers the Button node’s action, resolves its context paths against the current data model, and sends an action message to the agent.
